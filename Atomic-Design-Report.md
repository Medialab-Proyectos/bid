# Reporte de Revisión – Atomic Design
**Proyecto:** IF (Portal BID – Frontend Angular)
**Fecha:** 2026-04-08
**Ruta analizada:** `IF/src/app`

---

## 1. Resumen ejecutivo

El proyecto IF es una aplicación Angular de gran tamaño con **~270 componentes** (`*.component.ts`). La organización actual sigue un patrón **feature-based + shared module**, no una estructura Atomic Design explícita. Sin embargo, la mayoría de los componentes pueden mapearse a las cinco capas de Atomic Design (átomos, moléculas, organismos, templates y páginas).

**Veredicto general:**
- Buena separación entre `core/`, `shared/` y `features/`.
- El módulo `shared/components` concentra los bloques reutilizables, pero **mezcla átomos, moléculas y organismos sin distinción**.
- Existen señales de duplicidad (p. ej. `mat-*` vs equivalentes propios: `mat-numeric` / `input-numeric`, `mat-file-list` / `files-list`).
- Falta una capa formal de **átomos** (botón base, label, icono, tag) y de **templates** (layouts puros sin lógica).
- Las **páginas** están implícitas en cada `features/<x>/views/`.

---

## 2. Estructura actual del proyecto

```
IF/src/app
├── core/         → servicios, guards, store (NgRx), modelos, interceptores
├── shared/       → componentes, directivas, pipes, kendo, services
│   ├── components/   (≈ 50 carpetas de componentes reutilizables)
│   ├── directives/
│   ├── pipes/
│   └── kendo/
└── features/     → módulos de negocio
    ├── activities, autogenerated-forms, dashboard, disbursement-info,
    ├── eoi, forms, gpn, initial-queries, notifications,
    ├── procurement (con sub-features anidadas), projects, spn,
    ├── transactions, workflow
```

Cada `feature` contiene típicamente: `components/`, `models/`, `services/`, `views/`.

### 3.10 Resumen de hallazgos en Foundations

| Área | Estado | Acción sugerida |
|---|---|---|
| Color | ⚠️ Redundante (4 rojos, 2 escalas de gris) | Consolidar a una paleta única semántica |
| Tipografía | ⚠️ 2 familias, base 13 px | Unificar familia, subir base a 14/16 px |
| Espaciado | ⚠️ Escala con duplicado (2/2) y no múltiplo de 4 | Migrar a escala 4-based |
| Radius | ✅ OK | – |
| Shadows | ⚠️ Sin escala publicada | Definir `elevation-1..5` |
| Breakpoints | ✅ OK | Documentar |
| Z-index | ✅ Centralizado | – |
| Iconos | ❌ 3 sistemas | Elegir uno (recomendado: FA o sprites) |
| Theming | ⚠️ Bootstrap + Material | Decidir uno y migrar |

**Conclusión foundations:** existen los tokens, pero **no están auditados ni documentados como design tokens públicos**. Hay duplicidad histórica producto de migraciones (Bootstrap → Kendo → Material). Como paso previo a la reorganización Atomic Design, es crítico **consolidar y publicar los foundations** (idealmente como CSS variables o un paquete `@if/tokens`) para que átomos y moléculas los consuman de forma uniforme.

### 4.4 Templates (layouts puros)

**No existen formalmente.** El proyecto no tiene una carpeta `templates/` ni componentes que actúen como esqueletos sin lógica. La estructura de página se construye directamente dentro de cada `views/` mezclando layout + estado + datos.

Lo más cercano a "template" hoy es:
- `headers/` (header + sidebars) que envuelve la app a nivel global.
- `flows-sticky-footer` (estructura de footer fijo en flujos).

**Recomendación:** crear `shared/templates/` para layouts (`form-layout`, `list-layout`, `detail-layout`, `wizard-layout`).

## 5. Hallazgos principales

### 5.1 Fortalezas
1. **Separación core / shared / features** sólida y consistente.
2. **`shared/components/` modular**: cada componente tiene su sub-carpeta con `components/`, `models/`, `services/`.
3. Uso correcto de **NgRx en `core/store`** desacoplando estado de UI.
4. Existe un `ui-kit` (sandbox) que puede evolucionar a un Storybook real.
5. **Componentes de dominio bien encapsulados** (documents, dialog-comments, tables).

### 5.2 Debilidades / Riesgos
1. **Sin jerarquía Atomic Design explícita**: todo cae dentro de `shared/components` sin distinguir átomo, molécula u organismo.
2. **Duplicidad detectada:**
   - `input-numeric` ↔ `mat-numeric`
   - `mat-file-list` ↔ `files-list` (en `documents`)
   - `mat-doc-list` ↔ `docs-list`
   - `mat-finished-docs` ↔ `finished-docs`
   - `mat-file-select` ↔ `file-selector`
   Esto sugiere una migración inacabada de Material → componentes propios/Kendo.
3. **Falta de átomos base** (Button, Icon, Tag, Label, Typography). Hoy se confía en clases Tailwind + Kendo dentro de cada componente.
4. **Sin capa de templates**: layouts mezclados con lógica en `views/`.
5. **Anidamiento profundo en `procurement`** (`features/.../features/.../features/...`) reduce legibilidad.
6. **`shared/components/ui-kit`** existe como showcase manual, pero no hay Storybook ni documentación viva.
7. Carpetas inconsistentes: algunas usan `component/` (singular, p. ej. `dropdown-button`) y otras `components/`.

## 6. Recomendaciones

### 6.1 Reorganización propuesta (`shared/`)

```
shared/
├── atoms/
│   ├── button/
│   ├── icon/
│   ├── tag/
│   ├── label/
│   ├── avatar/                ← mover desde components/
│   ├── status-label/          ← mover
│   ├── loader-spinner/        ← mover
│   ├── input-currency/        ← mover
│   ├── input-numeric/         ← consolidar con mat-numeric
│   ├── input-phone/           ← mover
│   └── error-alert/           ← mover
├── molecules/
│   ├── dropdown-button/
│   ├── multiselect/
│   ├── form-title/
│   ├── confirm-cancel-dialog/
│   ├── no-content/
│   ├── card-header/
│   ├── profile-card/
│   ├── accordion-panel/
│   └── error-alert-list/
├── organisms/
│   ├── documents/
│   ├── dialog-comments/

│   ├── tables/

│   └── wizard-layout/
└── ui-kit/                    ← evolucionar a Storybook
```

Las **páginas** permanecen en `features/<x>/views/`.

### 6.2 Acciones técnicas
1. **Eliminar duplicidades `mat-*`**: decidir Kendo vs propio y borrar la otra implementación.
2. **Crear átomos base** (`Button`, `Icon`, `Tag`, `Typography`) antes de migrar el resto, para que las moléculas/organismos los reutilicen.
3. **Introducir Storybook** apuntando al nuevo `atoms/` y `molecules/`. Reemplaza `ui-kit.component`.
4. **Normalizar nombres**: siempre `components/` (plural), no `component/`.
5. **Aplanar `procurement`**: el anidamiento `features/features/features` debería reducirse a 2 niveles máx.
6. **Definir templates** y migrar las `views/` para que consuman layouts en lugar de redefinirlos.
7. **Documentar reglas Atomic Design** en `docs/` y reflejarlas en lint/PR checklist.
8. **Auditar `shared/kendo/`** para encapsular Kendo dentro de átomos propios y evitar el acoplamiento directo desde features.

### 6.3 Plan de migración por fases
1. **Fase 0 – Inventario y guía:** documentar la convención y publicar guía Atomic Design.
2. **Fase 1 – Átomos base:** crear `atoms/button|icon|tag|label|typography` + Storybook.
3. **Fase 2 – Mover átomos existentes:** avatar, status-label, inputs, loader, etc. (mantener barrels).
4. **Fase 3 – Moléculas y organismos:** mover en bloques + actualizar imports.
5. **Fase 4 – Templates:** extraer layouts desde `views/`.
6. **Fase 5 – Limpieza:** eliminar `mat-*` duplicados y `ui-kit` legacy.

## 8. Conclusión

El proyecto IF tiene una base sólida y modular, pero **no aplica Atomic Design de forma explícita**. Migrar a una estructura `atoms / molecules / organisms / templates / pages` —comenzando por crear los átomos base y eliminar duplicidades `mat-*`— mejoraría la consistencia visual, reduciría el bundle, facilitaría la incorporación de nuevos desarrolladores y permitiría documentar el sistema de diseño con Storybook. La complejidad actual (270 componentes) hace que esta inversión tenga **alto retorno** y es viable hacerla por fases sin bloquear el desarrollo de features.
